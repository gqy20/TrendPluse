# 后续功能开发说明

本文档用于统一管理 TrendPulse 后续功能的开发方式，避免需求分散在 issue、评论和临时文档中。

## 1. 适用范围

- 新增能力（如新的信号源、新报告类型、新通知渠道）
- 影响主流程的改造（pipeline、数据模型、工作流）
- 影响成本或稳定性的优化（并行策略、重试策略、质量门禁）

## 2. 文档放置规范

- 轻量改动（小于 2 天，单模块）：直接在 `docs/features.md` 增补小节。
- 中大型功能（跨模块或跨工作流）：新增独立文档，放在 `docs/` 根目录，文件名使用小写短横线，例如：
  - `docs/issue-quality-gate-plan.md`
  - `docs/discovery-ranking-v2.md`
- 需要长期跟踪的专题：单独文档 + README 增加一行入口说明。

## 3. 标准模板

每个后续功能文档建议包含以下章节：

## 背景与问题

- 当前现状（含时间范围和数据）
- 现有方案的核心问题
- 不做改造的风险

## 目标与非目标

- 目标（可量化）
- 非目标（明确本次不处理范围）

## 方案设计

- 数据流/模块改动点
- 配置项变更（含默认值）
- 与现有流程兼容策略

## 实施计划

- 阶段拆分（P0/P1/P2）
- 每阶段代码改动清单（文件级）
- 回滚方案

## 验收标准

- 功能验收条件
- 质量指标（如准确率、覆盖率、失败率、耗时）
- 测试清单（单测/集成/回归）

## 上线与运维

- GitHub Actions 变更
- 告警与观测指标
- 文档同步项（README、docs、脚本帮助）

## 4. 提交流程规范

1. 先提交开发说明文档，再进入实现。
2. 实现 PR 必须引用对应文档路径。
3. 文档更新与代码变更保持同步，避免“代码已变、文档滞后”。

推荐 commit 前缀：

- `docs:` 文档新增/更新
- `feat:` 新功能
- `fix:` 修复与稳定性增强
- `refactor:` 结构重构（行为不变）

## 5. 当前建议优先方向（示例）

1. Issue 洞察质量门禁：提升“用户痛点”识别准确率，降低泛化主题误报。
2. 信号质量监控：为日报增加高影响占比、覆盖度、解析成功率告警。
3. 运行时长优化：分阶段采集与分析并行化，缩短每日任务总耗时。
