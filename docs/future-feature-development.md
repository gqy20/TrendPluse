# 后续功能开发说明

本文档用于统一管理 TrendPulse 后续功能的开发方式，避免需求分散在 issue、评论和临时文档中。

## 1. 适用范围

- 新增能力（如新的信号源、新报告类型、新通知渠道）
- 影响主流程的改造（pipeline、数据模型、工作流）
- 影响成本或稳定性的优化（并行策略、重试策略、质量门禁）

## 2. 文档放置规范

- 轻量改动（小于 2 天、单模块）：直接更新 `docs/features.md`。
- 中大型或需持续跟踪的功能：新增独立文档放在 `docs/` 根目录，文件名使用小写短横线，例如：
  - `docs/issue-quality-gate-plan.md`
  - `docs/discovery-ranking-v2.md`
- 对外可见或长期执行的主题，再在 README 增加入口说明。

## 3. 标准模板

每个后续功能文档建议包含 6 个章节：

1. 背景与问题（现状数据 + 风险）
2. 目标与非目标（可量化目标）
3. 方案设计（改动点 + 兼容策略）
4. 实施计划（阶段拆分 + 回滚）
5. 验收标准（指标 + 测试）
6. 上线与运维（workflow/监控/文档同步）

## 4. 提交流程规范

1. 先有开发说明文档，再开始实现。
2. 实现 PR 必须引用对应文档路径。
3. 代码与文档同 PR 更新。

推荐 commit 前缀：

- `docs:` 文档新增/更新
- `feat:` 新功能
- `fix:` 修复与稳定性增强
- `refactor:` 结构重构（行为不变）

## 5. 路线优化方法（2026-02-24）

为避免路线只停留在 TODO 列表，采用以下统一方法：

1. 优先级框架：`WSJF = 延迟成本 / 工作量`。
2. 交付节奏：按 `Now / Next / Later` 分层，而不是长期固定 P0/P1/P2。
3. 准入和完成标准：每个条目都要有 DoR（开始条件）和 DoD（完成条件）。

### 5.1 WSJF 评分口径

- 延迟成本（CoD）由三项组成，按 1-10 评分：
  - 业务价值（Value）
  - 时间紧迫性（Time Criticality）
  - 风险降低/机会使能（Risk Reduction）
- 工作量（Job Size）按 1-10 估算。
- `WSJF = (Value + Time Criticality + Risk Reduction) / Job Size`

## 7. 路线执行规则

1. 进入 `Now` 的任务必须具备：
   - 对应 issue
   - 设计说明文档（`docs/<feature>-plan.md`）
   - 明确 DoD 与回滚方案
2. PR 描述必须包含：
   - 关联 issue 编号
   - 对应路线层级（Now/Next/Later）
   - 验收结果
3. 合并前最少检查：
   - 单测 + 关键集成测试
   - README/docs 同步
   - 关键指标回归无恶化
